## Development and configuration

Use Node 24.22.1 or later in the 24.x line and Python 3.13. The minimum Node version includes the CVE-2026-111497 Brotli decoder fix. Run `nvm install` and `nvm use` from the repository root if you use nvm; npm installs reject older runtimes. Install frontend dependencies with npm --prefix apps/web ci. In apps/api create a virtual environment and install -r requirements.lock. Native Django reads process environment, not .env. For local native use set DEBUG=true and USE_SQLITE=true, then migrate before running npm run dev from root. The launcher starts the API on 127.0.0.1:8000, Vite on 127.0.0.1:5173 and run_jobs. It does not install packages, migrate databases or seed fixtures automatically. Set PYTHON to a Python executable if needed. Compose remains independently usable from apps/api and loads apps/api/.env. Keep existing Compose project name/volume configuration when using an existing database; changing the directory can change Compose's default project name. Set COMPOSE_PROJECT_NAME to the previous project name or use -p explicitly. Back up databases before an eventual migration rollout.

Sanitized examples are apps/web/.env.example and apps/api/.env.example. Copy examples locally only as needed. Web VITE_* values are public. Backend runtime credentials must be supplied only to API, worker and migration components. No frontend import of Django/server credentials or modules was added. The local Node sandbox still uses its own test credentials and database under apps/web; do not point it at production or redirect it into Octagon.

## Routing and authentication

Vite proxies relative /api requests to Django on port 8000, with the existing /api/sandbox override to the opt-in Node server on port 4242. Django exposes /api/health/ and /api/stripe/webhook/ as aliases to the existing handlers. No JSON enrollment API existed, so the React demo's enrollment was not rewritten to call invented endpoints. Run npm run check:connectivity while dev is running to verify the health response and backend 404 behavior through Vite.

Octagon is also a server-rendered customer portal. Its existing /accounts/, /billing/, /enroll/, /octagon/, /photos/ and other routes retain their behavior, cookie authentication, CSRF and MFA. Locally use http://127.0.0.1:8000 for that portal. In production assign a separate portal hostname to the same API component, forwarding every path unchanged. This avoids collisions with the storefront's /enroll and root routes and keeps Django-generated absolute paths, OAuth/email links and Stripe return URLs intact. PUBLIC_BASE_URL must be that portal origin. Do not mount the entire portal under /api by stripping a prefix: its existing generated URLs assume root mounting.

App Platform ingress must route /api and /stripe/webhook to API before static fallback and route all portal-host requests to API. Preserve path prefixes. Both webhook aliases use the exact same signature-verifying handler. Unknown /api paths must stay backend 404s. Set Stripe's destination to the chosen HTTPS /api/stripe/webhook/ or existing /stripe/webhook/ and preserve the signing secret; do not create duplicate deliveries unnecessarily. Native Django /static/ is served by WhiteNoise on the portal host. Private uploads remain authorized PostgreSQL-backed views, never public static files. Cross-origin browser session APIs have not been introduced.

## DigitalOcean App Platform preparation

infrastructure/digitalocean.app.yaml is a local template, not a deployed app. It defines source_dir apps/web for the static component and apps/api for API, worker and pre-deploy migrations, with existing Dockerfile builds for Python. No shared dependencies cross those source directories. Replace example domains and register the intended storefront/portal domains in the app configuration when deployment is separately approved. GitHub source branch is main and automatic deployments are disabled; use the reviewed migration branch for a staging deployment if desired.

Before use, configure an existing managed PostgreSQL database and its POSTGRES_DB, POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_HOST and POSTGRES_PORT settings. Match required TLS policy to that database; the current application has no new database TLS adapter. Supply DEBUG=false, USE_SQLITE=false, SECRET_KEY, MFA_ENCRYPTION_KEY, ALLOWED_HOSTS (including health-check host as needed), CSRF_TRUSTED_ORIGINS, PUBLIC_BASE_URL, SMTP settings, Stripe keys/configuration, and business settings described in apps/api/.env.example and apps/api/docs/providers-and-policies.md. Share backend runtime settings with API, worker and migration job; never with web/build VITE variables. Existing production settings fail closed until configured. Review proxy HTTPS/security settings against the existing backend deployment guide before launch. Use the pre-deploy migration job against the existing backed-up database; never ship db.sqlite3. Keep one worker initially to retain existing task semantics. Private photo storage, audit records, authorization and webhooks were not refactored.

Reference: https://docs.digitalocean.com/products/app-platform/reference/app-spec/ (source_dir, Dockerfile, ingress preserve_path_prefix and worker/job schema). No infrastructure, DNS, secrets, repositories or production integrations were changed remotely.
