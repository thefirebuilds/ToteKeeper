# Security, access and retention

Customer mutations use verified identity and server-owned account links. User-supplied provider IDs, prices, roles and physical statuses never establish authority. CSRF applies to browser writes; only the signed Stripe endpoint is exempt. Staff console and Django admin require verified email, an enrolled strong factor and a session containing a completed allauth MFA challenge. Stewards are restricted to assigned deliveries; administrator privileges are provisioned explicitly. Django User admin role flags are read-only; use `provision_staff` from the trusted server shell with a reason.

Login lockouts use database-backed Axes after five failures for thirty minutes. Username and email normalize to the same internal user identity. Allauth rate counters use a shared database cache, not worker-local memory. `axes.W006` is intentionally silenced because account-based limiting works across rotated client IPs and avoids treating Caddy's internal address as every customer. Edge abuse controls remain advisable. Unlock a reviewed lockout using `python manage.py axes_reset_username user:USER_ID`.

Audit events include UTC timestamps, actor/type, affected account/record, outcome, redacted before/after fields, correlation IDs and provider event IDs. Audit/ledger admin screens are read-only and model-instance modification/deletion is rejected. Atomic request/service transactions prevent a successful mutation from silently losing its audit. Direct SQL, privileged QuerySet updates and database administrators can alter records; this is not tamper-proof storage. Restrict database credentials and admin access, and archive audit exports to separately controlled storage if stronger guarantees are needed. Customers never receive internal audit logs. Invoice, delivery and security notifications are separate.

Passwords, tokens, cookies, MFA secrets/recovery codes, image bytes, message bodies, addresses and phone numbers are excluded/redacted from audit payloads. Caddy/Gunicorn access logs are disabled; Django request/security, Axes and Stripe loggers are silenced to prevent URLs/tokens and personal data leaking. Health checks and job outcomes provide coarse monitoring; investigate failures through restricted provider/job state rather than dumping request bodies. Console email is development-only and contains real reset/verification tokens: use fictional data and control terminal access.

Photos are privately stored in PostgreSQL for this MVP, so backups contain them. No public media URL/storage bucket is exposed. Downloads require account ownership or assigned-staff authority. Uploads accept decoded JPEG/PNG/WebP only, up to 5 MB/20 megapixels and eight active images per item. Files are re-encoded without original metadata; filenames are generated UUIDs. Deletion immediately clears the live image bytes while preserving a tombstone/audit. Old backups may retain deleted data until backup expiry. Scale storage to a private object service with authorized signed URLs before large image volumes.

Initial engineering retention policy: sessions expire after twelve hours or browser closure; daily `clearsessions` removes expired rows. User-session metadata is purged by allauth during user-session management. Rate-cache entries expire by their individual limits and are culled by the cache backend; use normal database maintenance. Axes access/failure logs are disabled, with database attempts retained only as operational lockout state; review/purge stale attempts under the approved retention process. Notification jobs should be reviewed daily; after ten failed sends they remain visible for staff intervention. Email is at-least-once: a crash after sending but before committing may cause a duplicate, never a silent success marker.

Retain internal audit/ledger and financial metadata for an initial 12-month operational review period, with a launch-time legal/accounting retention review before purging any financial or contractual records. This app deliberately provides no ordinary audit-delete UI or automatic purge job. Administrators must approve/export/archive older records through a separate controlled maintenance process, honoring holds and applicable requirements. Restrict backups, define their off-host encrypted retention, and document deletion requests, including backup aging. Do not treat this engineering default as a legal retention determination.

## Lost MFA recovery

First use an existing passkey, another enrolled factor or an offline recovery code. Password reset does not remove MFA. If all factors are lost, create a restricted support case and independently verify identity under an operator-approved recovery procedure; possession of an email link or knowledge of an address alone is insufficient for staff recovery. Require a second administrator review for privileged accounts. Only a trusted server operator may then remove/re-enroll factors using the library's supported administrative process, revoke existing sessions, record the case/reason as an audit event, and send a separate security notification. Never request or log an old MFA secret/recovery code. This manual identity-review procedure must be finalized before production; there is no public MFA-reset endpoint or support-agent bypass.
